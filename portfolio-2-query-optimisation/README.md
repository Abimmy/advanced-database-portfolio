# Portfolio 2 — Query Processing and Optimisation (7 marks)

**Status:** Implemented and tested on MariaDB 10.4.32 (6 experiments, 12 measured query variants).

## Objective
Show how MariaDB executes MikePay queries, find the slow ones, improve them with an index or a rewrite, and prove each improvement with execution plans and measurements. No query is called "optimised" without a before/after comparison.

## Test environment
| Item | Value |
|---|---|
| Server | MariaDB 10.4.32 (XAMPP), InnoDB, isolation REPEATABLE-READ |
| InnoDB buffer pool | **16 MB** (XAMPP default, **not changed**) |
| InnoDB redo log file | 5 MB |
| Host | Windows 11, Intel Core i7-1265U (10 cores), 31.7 GB RAM; laptop in normal use during runs |
| Data | Synthetic, generated by [sql/01_generate_bulk_data.sql](sql/01_generate_bulk_data.sql) with fixed random seeds |
| Data volume | 50,008 customers, 80,009 accounts, 110,006 transfers (10,002 failed), **780,020 ledger rows**, 160,028 audit rows |
| Largest table | transactions: 43.6 MB data + 45.1 MB indexes, so it does **not** fit in the 16 MB buffer pool |

The data is skewed on purpose: low-numbered accounts are busier. Account 1001 has 2,218 ledger rows; other accounts have as few as 1. Bulk rows use ids from 1001 upward, so the nine Portfolio 1 rows are untouched.

The load took about 45 minutes on this machine (08:11 to 08:56 on 2026-11-04). It was slow because the 16 MB buffer pool forces constant disk reads. I did not change the server setting.

## Method
- **EXPLAIN** is the *estimated* plan; the query is not run.
- **ANALYZE** (MariaDB's equivalent of `EXPLAIN ANALYZE`) is the *actual* plan; the query is run and real row counts are reported.
- **Rows read** is the sum of the `Handler_read_*` status counters for one execution. It does not depend on machine load, so it is the most reliable measure.
- **Run time** is server-side `r_total_time_ms` from `ANALYZE FORMAT=JSON`. Each variant is run 6 times. *First run* is the first run after the index change (data may come from disk). *Median repeat* is the median of runs 2–6 (mostly cached).
- Statistics are refreshed with `ANALYZE TABLE` before each variant. Baseline states that need an index to be absent are produced by really dropping it, then restoring it. After the run the harness checks that the index list matches the original: **identical, YES**.
- One caveat on timings: the laptop was in use, so small differences are noise. Large differences and the rows-read counts are what matter.

## Results
Full tables: [evidence/02_benchmark_summary.md](evidence/02_benchmark_summary.md). Raw plans for every variant: [execution-plans/](execution-plans/).

| # | Query | Change | Plan before → after | Rows read | Median repeat time |
|---|---|---|---|---|---|
| E1 | Account lookup by account number | UNIQUE index restored | `ALL` (full scan) → `const` | 80,010 → 1 | 68.0 ms → 0.003 ms |
| E2 | Latest 20 transactions of a busy account | Composite index (account_id, created_at) instead of account_id only | `ref` + **filesort** → `ref`, no filesort | 2,219 → 20 | 216.5 ms → 0.157 ms |
| E3 | Monthly volume report | Covering index (created_at, transaction_type, amount) | `ALL` → `range`, **Using index** | 812,758 → 65,466 (12.4x fewer) | 571.0 ms → 59.3 ms (9.6x) |
| E4 | Single-day report | **Query rewrite only**: `DATE(created_at) = x` → range | `ALL` → `range` (same index in both) | 780,021 → 1,095 (712x fewer) | 502.4 ms → 2.4 ms (211x) |
| E5 | Transfers between two accounts | New index (source, destination) | `ref` → `ref` | 4 → 2 | 0.081 ms → 0.043 ms |
| E6 | Top 10 senders in Q1 2026 (join) | Covering index (status, created_at, source_account_id, amount) | `ref` → `range`, **Using index** | 52,366 → 52,366 (same) | 480.3 ms → 51.9 ms (9.2x) |

## What each experiment shows
- **E1, full scan vs index lookup.** Without the index MariaDB reads all 80,009 rows to find one account. With it, one row is read. The same unique index also enforces the "no duplicate account numbers" rule.
- **E2, composite index and sorting.** An index on `account_id` alone finds the 2,218 rows for the account but must read them all and **sort** them (`Using filesort`) to get the newest 20. The index on `(account_id, created_at)` already stores them in date order, so MariaDB reads the last 20 and stops. This is why Portfolio 1 defined that composite index. Note that `EXPLAIN` estimates 2,218 rows in *both* variants. Only the actual counters (2,219 vs 20) and the disappearance of `Using filesort` show the improvement, which is why estimates and measurements are kept separate.
- **E3, covering index.** The ledger had no index starting with `created_at`, so the report read all 780k rows. The covering index holds every column the query needs, so the table itself is never touched (`Using index`). `Using temporary; Using filesort` remains in both plans because the `GROUP BY` is on a column that is not the first index column. I did not test an index design that removes it.
- **E4, rewriting a non-sargable predicate.** The index on `created_at` exists in both variants, yet `WHERE DATE(created_at) = '2026-03-15'` cannot use it, because the column is wrapped in a function (`type=ALL, key=NULL`). Rewriting it as a half-open range gives the optimiser a range it can use, with no schema change at all. It is the biggest gain here that needed no new index.
- **E5, a hypothesis that did not hold.** I expected a (source, destination) index to beat the existing indexes. It did not matter: the optimiser had already picked `idx_transfers_destination`, which was selective enough on its own (4 rows read vs 2, both sub-millisecond). **Adding that index is not justified**, so it is not kept. This is a deliberate result: more indexes cost disk space and slow writes, so each one needs a measured reason.
- **E6, covering index with the same rows read.** Rows read stays at 52,366 because index entries are still counted when a covering index is used. The plan changes from `Using index condition` (fetch each row from the table) to `Using index` (no table access), and the median time drops from 480.3 ms to 51.9 ms. The timing is consistent with the saved table lookups; I have not isolated that cause with a separate test.

## Conclusions
- Indexes helped most where the query filtered on a column with no usable index (E1, E3) or needed sorted output (E2).
- A rewrite beat any index when the predicate hid the column from the optimiser (E4).
- A covering index helped a join/aggregate by avoiding table lookups (E6), even though the row counts did not change.
- A plausible index can be useless (E5). Measure first.
- I recommend adopting the E2 composite index (already in the Portfolio 1 schema), the E4 rewrite, and, if these reports run often, the E3 and E6 covering indexes. The DDL is in [sql/02_experiments.sql](sql/02_experiments.sql). They are **not** added to the live schema now: every experiment restores the original Portfolio 1 indexes.

## Limitations
- One machine, one dataset, and a deliberately small 16 MB buffer pool. With a larger pool the timings would be closer together, though the rows-read counts would not change.
- The write cost of extra indexes (slower inserts and updates, more disk) was **not measured**, so I only describe it as a general trade-off. The index build times are recorded but build time is not the same as per-write cost.
- Read queries only, single session. Concurrent behaviour is Portfolio 3.
- The skew in the data is synthetic. Real transfer patterns may differ.
- E1 and E2 baselines are produced by temporarily removing a Portfolio 1 index; they show what the cost would be without it, not a past real state.

## Issues met along the way
- The first bulk-load attempt failed immediately: MariaDB's sequence tables name their column `seq`, not `n`. Fixed in the script.
- The first benchmark run printed meaningless ratios (for example "9676x faster") from dividing by times near 0.0 ms, and my E5 note assumed a plan that the optimiser did not choose. I fixed the report formatting, reworded E5 as a tested hypothesis, and re-ran everything so the evidence comes from one consistent run.
